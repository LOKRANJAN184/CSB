## 1. The big picture

```
 ┌──────────────────────┐        HTTPS + JSON         ┌──────────────────────┐        ┌───────────────┐
 │  Phone (Android APK) │  ─────────────────────────▶ │  Vercel (Node.js)    │ ─────▶ │ MongoDB Atlas │
 │  or any web browser  │  ◀───────────────────────── │  Express API         │ ◀───── │  (database)   │
 │  HTML + CSS + JS     │                             │  server/             │        └───────────────┘
 └──────────────────────┘                             └──────────────────────┘
          ▲                                                      │
          │  new APK download                                    │ "what's the latest version?"
          │                                                      ▼
 ┌──────────────────────┐   push tag v2.1.0     ┌───────────────────────────────┐
 │  GitHub Releases     │ ◀──────────────────── │  GitHub Actions builds APK     │
 └──────────────────────┘                       └───────────────────────────────┘
```

There are **three programs**:

| Part | Where it runs | Written in | Folder |
|---|---|---|---|
| **Frontend** (what you see) | On the phone, inside the APK (or in a browser) | HTML, CSS, JavaScript | `public/` |
| **Backend / API** (the brain) | On Vercel's servers | Node.js + Express | `server/`, `api/` |
| **Database** (the memory) | MongoDB Atlas | — | (cloud) |

The phone **never** talks to the database directly. It asks the API
("save today's sales"), the API checks you're allowed, then the API talks to
MongoDB. That's what keeps the data safe: the rules live on the server, where
nobody can tamper with them.

## 3. How a request travels

Let's follow **"the manager taps Save sales"** all the way through.

**① The screen** — `public/js/screens/sales.js`
The form keeps everything in one object called `form`. The Save button calls:
```js
await api(`/api/sales/${date}`, { method: 'PUT', body: form });
```

**② The API client** — `public/js/api.js`
`api()` adds three headers and sends the request:
```
Authorization: Bearer eyJhbGciOi…   ← "this is who I am" (login token)
X-Device-Id:   dev_4f1c…            ← "this is which phone"
X-Branch-Id:   6b07…                ← "this is which shop"
```
If the server answers 401 (token expired) it automatically logs you out.

**③ Vercel** — `vercel.json` sends every `/api/...` URL to `api/index.js`, which is
just our Express app.

**④ Express app** — `server/app.js`
Runs in order: CORS → JSON body parser → "connect to MongoDB" → the matching
router. `/api/sales/...` → `server/routes/sales.js`.

**⑤ Middleware** — `server/middleware/auth.js` → `authenticate`
- verifies the token signature (was it really issued by us? not expired?)
- loads the user from MongoDB
- **manager only:** is `X-Device-Id` the approved device? If not → 403.
- works out the branch (managers are locked to their own).
- puts `req.user`, `req.branchId` on the request for the route to use.

**⑥ The route** — `server/routes/sales.js` → `router.put('/:date')`
- validates the date; managers can only edit **today** (`canEditDate`)
- cleans every number with `money()` (no negatives, no "abc")
- saves → Mongoose `pre('save')` hook recalculates the tally
- writes audit log entries for every field that changed
- answers `{ ok: true, record }`

**⑦ Back on the phone** the screen shows a toast: "Saved — tallied!"

If anything throws an error anywhere in ⑤–⑥, Express 5 catches it and the one
error handler at the bottom of `server/app.js` turns it into
`{ ok: false, code, message }`. That's why routes have no `try/catch`.

## 4. The backend

### Express in 60 seconds
```js
const router = express.Router();
router.get('/:date', async (req, res) => {        // GET /api/sales/2026-11-25
  const record = await DailySales.findOne({ date: req.params.date });
  res.json({ ok: true, record });
});
```
- `req.params` — parts of the URL (`:date`)
- `req.query` — `?month=2026-11`
- `req.body` — JSON sent by the app
- `res.json()` — send the answer

**Middleware** is a function that runs before the route:
`router.use(authenticate, requireSingleBranch)` means "every route in this file
needs a logged-in user and a specific branch".

### The API at a glance

| Method & path | Who | What |
|---|---|---|
| `POST /api/auth/login` | anyone | owner: phone + PIN · manager: branch + PIN + device |
| `GET /api/auth/me` | logged in | is my session still valid? |
| `GET/PUT/DELETE /api/auth/owner-phones/:phone` | owner | owner login phones & PINs |
| `GET /api/branches` | anyone | branch list for the login screen |
| `GET /api/branches/manage` | owner | branches + manager + device status |
| `POST /api/branches`, `PUT /api/branches/:id` | owner | create / edit branch |
| `PUT /api/branches/:id/manager` | owner | set manager PIN |
| `POST /api/devices/:branchId/:action` | owner | approve / reject / remove / block / unblock |
| `GET/PUT /api/sales/:date` | both | daily tally |
| `POST /api/photos`, `GET /api/photos/:id` | both | bill photos |
| `GET/PUT /api/attendance/:date` | both | daily attendance |
| `GET/POST/PUT/DELETE /api/staff` | both (salary: owner only) | staff |
| `GET /api/reports/calendar?month=` | both | dots on the Records calendar |
| `GET /api/reports/monthly?month=` | owner | month totals + salary |
| `GET /api/reports/sales?from&to` | owner | sales range (branch or all) |
| `GET /api/reports/attendance?from&to` | owner | attendance & salary range |
| `GET /api/reports/sales.pdf`, `attendance.pdf` | owner | PDFs |
| `GET /api/history` | owner | audit log ("Edit history") |
| `GET /api/app/latest` | anyone | latest APK version (for updates) |
| `GET /api/health` | anyone | is the server + database OK? |

### Important ideas in the code

**One place for settings** (`server/config/env.js`). Never write a password or
secret in code — read it from an environment variable. Locally they come from
`.env`; on Vercel from Project → Settings → Environment Variables.

**"Today" uses India time** (`server/lib/dates.js`). Vercel's servers run on UTC,
which is 5½ hours behind India. Without this, between midnight and 5:30 AM the
server would think it was still yesterday and block the manager.

**Validate everything from the phone.** `money()` turns any input into a safe
number; `str()` trims and limits length. Never trust what the client sends —
someone could send `systemSales: -99999` with a hand-made request.

**Audit everything** (`server/services/audit.js`). Every create/update/delete
writes an `AuditLog` row: who, what, old value → new value, when. If logging
fails it only prints a warning — it must never break the real save.

**Photos live in MongoDB** (`server/services/photos.js`, `models/Photo.js`).
Vercel's disk is read-only and wiped between requests, so saving files to disk
(what the old app did) silently loses them. Photos are shrunk twice: first on
the phone (`compressImage` in `ui/components.js`), then by `sharp` on the server
to ~100 KB WebP.

**PDFs** (`server/services/pdf.js`). One generic `buildReportPdf({ title,
summary, columns, rows })` draws every report. It embeds the Anek Tamil font, so
Tamil staff names print correctly.

## 5. The database

MongoDB stores **documents** (JSON-like objects) in **collections**. Mongoose
lets us describe the shape of each document with a **schema**.

| Collection | One document = | Key fields |
|---|---|---|
| `branches` | a shop | name, code, address |
| `users` | a login | role (owner/manager), hashed PIN(s), approvedDevice |
| `staffs` | a worker | name, role, dailySalary, isActive, branchId |
| `dailysales` | one branch, one day | systemSales, totalCash, totalGpay, expenses[], difference |
| `attendances` | one branch, one day | records[] = {staffId, status, inTime, outTime} |
| `photos` | a bill photo | data (binary WebP), branchId |
| `auditlogs` | one change | module, action, oldValue, newValue, performedBy |

**The tally rule** lives in exactly one place — `DailySales.computeTally()`:
```
accounted  = expenses + cash + gpay
difference = accounted − systemSales      (+ excess, − shortage, 0 = tallied)
```

**Unique index** `{ branchId: 1, date: 1 }` on sales and attendance means the
database itself refuses two entries for the same shop on the same day.

**Dates are strings** `'YYYY-MM-DD'`. That avoids time-zone bugs and makes
range queries simple: `{ date: { $gte: '2026-11-01', $lte: '2026-11-30' } }`.

**Staff are never deleted**, only `isActive: false` — so old attendance and
salary reports still show their names.

## 6. Security

### PINs are hashed
We never store the PIN itself. `bcrypt.hash('1234')` turns it into something like
`$2b$10$Xk…` that cannot be reversed. At login, `bcrypt.compare()` checks the
typed PIN against the hash.

### Login tokens (JWT)
After a correct PIN the server returns a **JSON Web Token**: a small signed note
saying "user 6b07…, role manager, device dev_4f1c…, expires 21:45". The phone
sends it with every request. Because it's signed with `JWT_SECRET`, changing even
one letter makes it invalid. Owner sessions last 5 hours, manager sessions 1 hour
(change in env: `OWNER_SESSION_HOURS`, `MANAGER_SESSION_HOURS`).

### Device lock (managers)
1. Manager types the right PIN on a new phone → the server saves it as
   `pendingDevice` and refuses with `DEVICE_PENDING`.
2. Owner opens **More → Branches & devices** → Approve.
3. Now that phone can log in. The device id is baked into the token **and**
   checked on every request, so copying the token to another phone is useless.
4. Approving a new device replaces the old one (only one per branch).

### Lockout
8 wrong PINs → that account is locked for 10 minutes. A 4-digit PIN has only
10,000 combinations; without this, a script could guess it in minutes.

### Manager can't see salaries
The server **removes** `dailySalary` from staff data for managers
(`routes/staff.js → view()`). Hiding it only in the UI wouldn't be enough —
anyone can read network responses.

### PDF links
A browser can't send our `Authorization` header, so for PDFs we ask the server
for a **2-minute download token** and put it in the URL. It only works for
downloads and expires fast.

### ⚠️ Your old PINs are public
The old code had the PINs written in it, and the GitHub repo is **public**, so
they're visible in the git history forever. After this version is live:
**More → Owner login PINs → change every PIN**, and **Branches & devices → Set
new manager PIN** for each branch.

## 7. The frontend

No framework (React/Vue) and no build step — plain modern JavaScript modules.
That keeps it small, fast on cheap phones, and easy to read. Every file is
loaded directly by the browser with `import`.

### Start-up — `js/main.js`
1. Apply the saved theme.
2. If there's a saved session → `startApp()`, otherwise `showLogin()`.
3. `startApp()` builds the shell (top bar, content area, bottom tabs) and calls
   `route()`.

### Routing
The screen is chosen from the URL **hash**: `#/sales/2026-11-25`. `ROUTES` in
`main.js` maps patterns to screen files. Screens are loaded only when first
opened (`import('./screens/sales.js')`), so start-up is quick.

Every screen is a function that receives a `ctx`:
```js
export default async function salesScreen(ctx) {
  ctx.setTitle('Daily sales', ctx.branchName);   // top bar
  ctx.params.date                                 // from the URL
  ctx.navigate('/sales/2026-11-24');              // go somewhere
  ctx.setGuard(() => dirty && 'Unsaved changes…'); // warn before leaving
  mount(ctx.root, ...elements);                   // draw
}
```

### Building the screen: `h()`
```js
h('button', { class: 'btn btn--primary', onclick: save }, icon('check'), 'Save')
```
creates `<button class="btn btn--primary">✓ Save</button>` with a click handler.
Text is always inserted as **text**, never as HTML — so if someone names a staff
member `<img onerror=…>`, it just shows those characters. This prevents **XSS**
attacks. (The old app built HTML strings with `innerHTML`, which is risky.)

### Don't re-draw inputs while typing
In `sales.js`, typing in "Cash" updates `form.totalCash` and repaints **only the
tally card**. The inputs stay in place, so the keyboard never closes and the
cursor never jumps.

### Shared pieces (`js/ui/`)
- `components.js` — `dateBar`, `moneyField`, `segmented`, `notice`, `empty`,
  `skeleton`, `compressImage`
- `sheet.js` — bottom sheets built on the native `<dialog>` element (free focus
  trap, Esc key, backdrop). `confirmSheet()` replaces `confirm()`.
- `toast.js` — short messages at the top
- `pinpad.js` — the big PIN keypad
- `icons.js` — inline SVG icons (no emoji, no icon font)

### Talking to the server — `js/api.js`
One function, `api(path, { method, body, branchId })`. It adds headers, sets a
20-second timeout, turns errors into readable messages ("You are offline…"), and
logs out on 401.

## 8. The design system

Built from the ui-research repo's guidance (docs/foundations, docs/components).

**Concept:** "the shop's evening ledger" — a calm, number-first tool used with one
thumb at closing time. Colours come from the **logo**: royal blue for actions,
gold for "today", vermilion for "money is off", and green used for **one**
meaning only: "tallied".

**Three layers of tokens** (`css/app.css`):
1. **Primitives** — raw colours in OKLCH: `--brand-600: oklch(47% 0.15 262)`
2. **Semantic** — role names that switch for dark mode:
   `--action: light-dark(var(--brand-600), var(--brand-400))`
3. **Components** — `.btn--primary { background: var(--action) }`

Change `--brand-h: 262` and the whole app re-colours.

**Rules followed** (from the research):
- Touch targets ≥ 44–48 px; primary actions in the bottom third (thumb zone);
  ≤ 5 bottom tabs.
- `font-variant-numeric: tabular-nums` so ₹ amounts line up.
- Only 3 radii (8 / 16 / pill). Motion 140–240 ms, ease-out, never
  `transition: all`. One "signature" animation: the ✓ stamp when the tally matches.
- `env(safe-area-inset-*)` padding so nothing hides under the notch/gesture bar.
- `prefers-reduced-motion` respected; `forced-colors` gets borders.
- Labels always visible above fields (no placeholder-as-label).
- Font: **Anek Tamil** (Tamil + Latin in one family), shipped inside the APK.

## 9. The Android app

**Capacitor** wraps the `public/` folder in a native Android app. Inside, it's a
full-screen browser (WebView) showing our HTML. Native extras come from plugins:

| Plugin | Used for |
|---|---|
| `@capacitor/app` | read the installed version, Android back button |
| `@capacitor/browser` | open APK downloads and PDFs in the system browser |

`js/lib/native.js` wraps them so the same code also works in a normal browser.

Because the web files are **inside** the APK, the app calls the live server by
full address — `PRODUCTION_API` in `js/config.js`. (Long-press the logo on the
login screen to point a test build at another server.)

**Commands** (need Node 22+, JDK 21, Android SDK):
```bash
npm run cap:sync          # copy public/ into android/ and update plugins
npm run apk               # build a signed release APK locally
npx cap open android      # open in Android Studio
```
`android/app/build.gradle` reads `versionName` from `package.json` and the
signing key from `~/chendurar-signing/keystore.properties` (or env vars in CI).

## 10. In-app updates

```
you:            npm run release -- patch "Fixed photo upload"
                    │ bumps 2.0.0 → 2.0.1, commits, tags v2.0.1, pushes
GitHub Actions: builds signed APK → GitHub Release "v2.0.1" with Chendurar-Bakery.apk
phone opens app:  GET /api/app/latest  →  server asks GitHub  →  { version: "2.0.1", apkUrl }
                  installed 2.0.0 < 2.0.1  →  banner "Version 2.0.1 is available" [Update]
user taps Update: opens apkUrl in the browser → downloads → tap → Android "Install update?"
```

**The signing key matters.** Android only installs an update over the old app if
both are signed with the **same key**. Your key is in `~/chendurar-signing/`.
**Back up that folder.** If it's lost, every phone must uninstall and reinstall.

**Why can't the app install silently?** Android doesn't let apps install other
apps without the user tapping "Install" (outside the Play Store). The first time,
Android asks to allow "Install unknown apps" for the browser — say yes.

**Changes that don't need an APK:** anything in `server/` goes live as soon as
Vercel deploys (on every push to `main`). Only changes in `public/` (screens,
styles) need a new APK release — though web users see them immediately.

## 11. Deploying

### Vercel (backend + web app)
- Connected to the GitHub repo; **every push to `main` deploys to production**
  (`https://csb-three.vercel.app`). Pushes to other branches get a preview URL.
- `vercel.json`: `/api/*` → the serverless function `api/index.js`; everything
  else → `public/`.
- Environment variables (Vercel → Project → Settings → Environment Variables):
  `MONGODB_URI`, `JWT_SECRET` (required); optional ones listed in `.env.example`.
- Check health: open `https://csb-three.vercel.app/api/health`.

### MongoDB Atlas
- Network Access must allow `0.0.0.0/0` (Vercel's IP addresses change).
- The connection string is in `MONGODB_URI`. If the password has special
  characters (`@ # %`), URL-encode them.

### GitHub
- `.github/workflows/test.yml` — runs the API tests on every push.
- `.github/workflows/release.yml` — builds and publishes the APK on `v*` tags.
- Secrets needed for releases (run once: `bash scripts/upload-signing-secrets.sh`):
  `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`,
  `ANDROID_KEY_PASSWORD`.

## 12. Everyday tasks

**Run it on your computer**
```bash
cp .env.example .env            # then fill in MONGODB_URI (a local DB is safest) and JWT_SECRET
npm install
npm run dev                     # http://localhost:5000, restarts when you save a file
```
An empty database is seeded once with an owner + manager — the PINs are printed
in the terminal (or set `SEED_OWNER_LOGINS` / `SEED_MANAGER_PIN`).

**Add a field to the sales form** (e.g. "Card payments")
1. `server/models/DailySales.js` — add `totalCard: { type: Number, default: 0 }`
   and include it in `computeTally`.
2. `server/routes/sales.js` — add `totalCard: money(body.totalCard)` to `next`.
3. `public/js/screens/sales.js` — add it to `form`, add a `moneyField`, include it
   in `updateTally`.
4. `server/routes/reports.js` → `sumSales` — add it to the totals.
5. Write a test in `test/api.test.js`, run `npm test`, then release.

**Add a new screen**
1. Create `public/js/screens/myscreen.js` exporting `default async function (ctx)`.
2. Add a line to `ROUTES` in `public/js/main.js`.
3. Link to it, e.g. from `more.js`: `link('#/myscreen', 'info', 'My screen')`.

**Change the colours** — edit `--brand-h` (and friends) at the top of `css/app.css`.

**Release an update** — commit your work on `main`, then
`npm run release -- patch "what changed"`. Watch GitHub → Actions.

**Someone forgot the manager PIN** — owner: More → Branches & devices → Set new
manager PIN.

**Manager got a new phone** — they log in on it once; owner approves it in
Branches & devices (it replaces the old phone).

## 13. Testing

`npm test` runs `test/api.test.js` against a **throwaway local database** (it
never touches Atlas). It starts the real app, then checks: logins, wrong PINs,
device approval, salary hidden from managers, photo compression, the tally maths,
"managers can't edit past days", PDF downloads, PIN change, history, lockout.

Needs MongoDB running locally (`.tools/bin/mongod --dbpath data/db --fork …`, or
Docker `docker run -p 27017:27017 mongo:7`). On GitHub the test workflow starts
MongoDB automatically.

Make it a habit: **change something → `npm test` → commit**.

## 14. What was wrong with the old version

| Problem | Why it mattered | Fix |
|---|---|---|
| PINs hard-coded in the code, repo public | Anyone could log in as owner | PINs only in the DB (hashed), changeable in-app |
| Server reset the owner PIN on **every start** | Changing your PIN never stuck | Seed runs only on an empty DB |
| Default JWT secret in code | Tokens could be forged | Required env var in production |
| Bill photos saved to Vercel's disk | Photos silently lost | Stored in MongoDB |
| Socket.io "real-time" on Vercel | Serverless can't hold sockets — never worked | Removed; screens refresh on open/resume |
| APK pointed at `11.12.22.235:5000` (a home IP) | App couldn't reach the live server | Uses `https://csb-three.vercel.app` |
| GitHub build failing on every push | No update ever reached phones | New workflow, Node 22, signed APK |
| Debug-signed APK | Updates can't install over each other | One permanent release key |
| "Today" in server (UTC) time | Manager blocked 00:00–05:30 | India time zone |
| 3,600-line `app.js` + `innerHTML` strings | Hard to change, XSS risk | Small screen files + safe `h()` helper |
| Tally maths in 3 places | Could disagree | One `computeTally()` |
| No tests | Every change was a gamble | `npm test` + CI |
| No brute-force protection | 4-digit PIN guessable | Lockout after 8 tries |

## 15. Glossary

- **API** — the set of URLs the app calls to read/save data.
- **Endpoint / route** — one of those URLs, e.g. `PUT /api/sales/:date`.
- **Middleware** — code that runs before a route (login check, etc.).
- **JWT** — signed login token.
- **Hash (bcrypt)** — one-way scrambling of a PIN.
- **Schema / model** — the shape of a database document (Mongoose).
- **Serverless** — Vercel runs our code only when a request arrives; no server
  stays on, so no files or open connections survive between requests.
- **Environment variable** — a setting given to the program from outside the
  code (`MONGODB_URI`), so secrets never live in git.
- **CORS** — browser rule about which websites may call an API.
- **WebView** — the browser engine inside the Android app.
- **Capacitor** — tool that turns a web app into an Android/iOS app.
- **APK** — Android app install file. **Signing key** — proves updates come from you.
- **CI (GitHub Actions)** — robots that test/build on GitHub after every push.
- **Tag / release** — a named version in git (`v2.0.1`) / its downloadable build.
- **Design token** — a named design value (`--action`) used instead of raw colours.
- **XSS** — attack where text gets run as code in someone's browser.
